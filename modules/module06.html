THE LECTURE · 45 MIN

Think in systems, not just models

Defense in depth

No single classifier, prompt, or filter can reliably recognize every attack. Build several independent layers: minimize data, separate instructions from content, restrict tools, validate outputs, log sensitive actions, and prepare a human fallback. If one layer fails, the next should still limit harm.

Prompt-level protection and CaMel

Prompt defenses aim to help a model distinguish trusted instructions from untrusted content. Research systems such as CaMel explore structured ways to make the model more resilient to prompt injection. Such methods can improve resistance, but they should be paired with application-side access control; the model should not be the only barrier between an attacker and a secret or powerful tool.

Verifiable execution

A trusted execution environment (TEE) uses hardware isolation to protect code and data while computation runs. Remote attestation can provide evidence about the environment or software measurement. A SNARK (succinct non-interactive argument of knowledge) can let a prover demonstrate that a computation follows a defined relation without asking a verifier to redo all of it. Proofs have limits: the circuit may not represent the whole system, and proving large neural computations can be expensive.

Independent review adds evidence

A third-party audit can review data handling, model access, software supply chains, security controls, and evaluation results. It is a point-in-time assessment against a stated scope, not a guarantee that a system is secure forever. Ask what was in scope, what was excluded, and how findings were retested.

Code generation still needs review

AI-generated code can contain injection flaws, insecure defaults, missing authorization, or vulnerable dependencies. Review it like any untrusted contribution: understand the data flow, use established libraries, run static and dependency analysis, add focused tests, and inspect the behavior around authentication, secrets, and error handling.

CASE NOTE · TRUST WHAT CAN BE CHECKED

A hosted inference provider says a model ran in a protected environment. A TEE attestation may help verify which code or configuration was loaded, but it does not prove that the model’s answer is correct, that the application made the right authorization decision, or that the hardware is free from every side channel. Ask exactly which claim is being verified and what remains trusted.

Stuck? Open the worked solution
  • The client-supplied user field is untrusted. Derive identity from a verified session on the server.
  • Authenticate the request and authorize what that user may ask or retrieve before calling the model.
  • Apply input size and content limits; avoid logging raw sensitive prompts by default.
  • Treat model output as untrusted text. Encode it for the output context and validate structured data against a schema.
  • Require a separate policy check and explicit human approval for consequential writes.
  • A suitably narrow attestation claim could be: “The request ran the stated inference service image and configuration in an attested TEE.” It does not prove answer correctness, safe application behavior, or freedom from all hardware attacks.

END OF MODULE 06

Keep these ideas

  • Use layered controls; do not make a prompt the only security boundary.
  • TEEs and attestation support specific execution claims, not correctness guarantees.
  • SNARKs can verify defined computations, with cost and scope limits.
  • Review generated code for identity, authorization, input handling, secrets, and dependencies.
