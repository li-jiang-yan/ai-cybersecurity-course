THE LECTURE · 40 MIN

Think in systems, not just models

Different models, different jobs

A task-specific model is trained or tuned for a narrower job, such as classifying a transaction as suspicious. A foundation model is trained on broad data and adapted to many tasks through prompts, fine-tuning, or additional components. Foundation models are flexible, but flexibility makes their behavior harder to bound with a single rule.

RAG: give the model a reference shelf

Retrieval-augmented generation (RAG) looks up relevant documents and includes them as context for a model response. A typical request passes through identity checks, retrieval, a language model, and an output. RAG can make answers more grounded and current. It also means document permissions, indexing pipelines, and retrieved text become security-critical. A malicious instruction hidden in a document can try to influence the model.

Agents: words connected to actions

An agent combines a model with tools, state, and a loop: observe, decide, act, then observe again. A search tool may only read. A calendar tool may write. A shell or payment tool can have much greater impact. Tool permissions should follow least privilege, and sensitive actions should have explicit policy checks and human approval. A model’s good intentions are not an access-control mechanism.

CASE NOTE · TRACE THE TRUST BOUNDARIES

Suppose an internal policy assistant searches employee documents. The user, search index, retrieved text, model provider, and answer screen are separate trust zones. A document can be visible to one employee but not another. The retrieval layer must enforce that difference before content reaches the model; hiding a citation after generation is too late.

  1. Sketch five boxes: employee, application, document store, language model, and answer screen.
  2. Connect them in order. Label every arrow with the data that moves across it. Include the employee identity and document text.
  3. Add a lock/check at the document store. Write which identity is used to decide whether a document may be retrieved.
  4. Add a boundary around the model. Note what the provider receives, how long it is retained, and whether it may be used for training. If you do not know, mark it as an open question.
  5. Add a “stop before action” gate anywhere a response could trigger a consequential action.
  6. Draw one malicious document entering the store and mark where it can be detected, quarantined, or prevented from influencing an answer.

Stuck? Open the worked solution
  • Check identity at the application and filter every document retrieval using the current user’s permissions.
  • Treat document text as untrusted input. Label and separate it from trusted instructions; do not assume a model can reliably distinguish them.
  • Send only the minimum context required. Confirm provider retention and training terms before production use.
  • Validate model output against a schema and application policy. Never let generated text directly grant access.
  • Require a human confirmation for external or high-impact writes.
  • Monitor retrieved sources, denied access attempts, tool calls, and unusual output patterns; make it possible to remove or re-index a suspect document.

END OF MODULE 02

Keep these ideas

  • Architecture determines where information and authority flow.
  • RAG introduces document permissions and retrieved-content risks.
  • Agents inherit the risks of every tool and permission they can use.
  • Keep authorization and action checks in deterministic application code.
